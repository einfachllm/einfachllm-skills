# Upgrade & rollback (Kubernetes)

## Upgrade

1. **Take or verify a database backup** (docs/backup.md). Migrations run
   forward automatically; a backup is the only universal way back.
2. Roll the release with an **immutable tag**:

   ```bash
   helm upgrade einfachllm deploy/helm/einfachllm --set image.tag=<git SHA> ...
   ```

   Migrations apply before the new pods serve (init container or hook Job).
   Config and secret changes roll pods via checksum annotations.
3. Verify:

   ```bash
   kubectl rollout status deploy/einfachllm
   curl -fsS localhost:8000/health
   # plus GET /admin/api/providers/health for upstream reachability
   ```

Never deploy a moving tag (`latest`, `dev`) to production — a rollback then has
nothing deterministic to go back to.

## Rollback

`helm rollback` restores the previous manifests and image, **but Helm never
downgrades the database schema**. `alembic upgrade head` is forward-only, and a
hook-Job rollback simply re-runs `upgrade head` (a no-op).

The safe sequence:

1. Roll back the release:

   ```bash
   helm rollback einfachllm <revision>
   # or: helm upgrade ... --set image.tag=<previous SHA>
   ```

2. **Usually leave the schema at head.** Migrations are reviewed to be
   additive and backward-compatible where possible, so old code on a new schema
   is the expected, tested direction.
3. Only if the new schema *itself* is the problem, downgrade explicitly — one
   revision at a time, gateway scaled down, backup in hand:

   ```bash
   kubectl scale deploy/einfachllm --replicas=0
   DATABASE_URL=... uv run alembic downgrade -1
   helm rollback einfachllm && kubectl rollout status deploy/einfachllm
   ```

   Caveats: `downgrade` is lossy by design; autogenerated `downgrade()`
   functions get less review than `upgrade()` — read the revision file first;
   never downgrade past the revision the running code expects. When in doubt,
   restore the backup instead.

Scaling to zero is a full outage. Say that out loud before proposing step 3,
and get explicit confirmation.

## Continuous deployment (self-hosted k3s)

`.github/workflows/deploy.yml` redeploys on every **green push to `main`**: it
fires after the `CI` workflow succeeds (a `workflow_run` gate), builds the
image, pushes it to GHCR, and runs `helm upgrade --install`.
`workflow_dispatch` runs the same job on demand.

It runs on a **self-hosted runner** with cluster access, because a home cluster
behind NAT is unreachable from GitHub's cloud runners (building there also
matches the node architecture).

One-time setup:

1. **Runner** — repo → Settings → Actions → Runners, labelled
   `self-hosted,macmini`. Install `docker`, `helm`, `kubectl`; point
   `KUBECONFIG` at k3s (`/etc/rancher/k3s/k3s.yaml`).
2. **Repo secrets** — `EINFACHLLM_MASTER_KEY` and one secret per provider
   `${VAR}` in `config/providers.yaml`. They are injected at `helm upgrade`
   time and never live in the repo.
3. **GHCR pull** — make the package public, or create the pull secret once:

   ```bash
   kubectl -n einfachllm create secret docker-registry ghcr \
     --docker-server=ghcr.io --docker-username=<you> \
     --docker-password=<PAT with read:packages>
   ```

   The workflow sets `imagePullSecrets[0].name=ghcr`; drop that flag if the
   package is public.

CI (GitHub Actions, US) only builds and tests — production runs on the
operator's own EU/on-prem cluster. Keep it that way.
