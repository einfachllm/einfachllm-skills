# Database migrations

Production schema is managed by [Alembic](https://alembic.sqlalchemy.org/).
Dev and tests still call `Base.metadata.create_all()` at startup, so a fresh
SQLite database needs no migration step.

**`create_all` only creates missing tables — it never adds a column to an
existing one.** Once a database outlives a schema change, it must be under
Alembic.

The schema is defined as SQLAlchemy 2.0 ORM models in
`src/einfachllm/db/models.py`; Alembic reads `Base.metadata`, so autogenerate
sees exactly what the application uses.

## Applying migrations

Alembic reads `DATABASE_URL` from the environment — the same variable the
application uses — so migrations and the app always target the same database.

```bash
DATABASE_URL=postgresql+asyncpg://user:pass@host/db uv run alembic upgrade head

uv run alembic current            # current revision
uv run alembic upgrade head --sql # pending migrations as SQL, no DB connection
uv run alembic downgrade -1       # roll back one revision (see the caveats below)
```

`alembic upgrade head` is idempotent — a no-op once the database is at head.

Apply it **before** the new version serves traffic.

## In Kubernetes

The gateway image includes the `alembic` binary (a runtime dependency, not a
dev one), so no second image is needed. Two modes, set by `migrations.mode`:

| Mode | Value | When |
| --- | --- | --- |
| Init container (default) | `migrations.mode=initContainer` | `replicaCount: 1` — simplest correct setup |
| Pre-upgrade hook Job | `migrations.mode=job` | several replicas or the HPA — migrates exactly once per rollout |

At `replicaCount > 1` the default would run `alembic upgrade head` in **every**
replica. Switch to the Job:

```bash
--set migrations.mode=job
```

Caveat: on a **first install** the hook runs before any other resource, so it
cannot wait for the in-cluster `postgresql` subchart. The chart rejects
`mode=job` + `postgresql.enabled=true` at install time. Upgrades are fine, and
`externalDatabase.url` works for both. The Job inlines `DATABASE_URL` (or uses
`secrets.existingSecret`), is bounded by `migrations.job.activeDeadlineSeconds`
(default 600), and failed Jobs are kept for debugging until the next rollout
replaces them.

For a hand-rolled manifest, an init container is:

```yaml
initContainers:
  - name: migrate
    image: einfachllm:latest
    command: ["alembic", "upgrade", "head"]
    env:
      - name: DATABASE_URL
        valueFrom: { secretKeyRef: { name: einfachllm-db, key: url } }
```

## Downgrades are a last resort

`alembic downgrade` is **lossy by design** — dropped columns and tables take
their data with them — and autogenerated `downgrade()` functions get far less
review than `upgrade()`. Read the revision file before running one.

Never downgrade past the revision the running code expects. Prefer restoring a
backup (docs/backup.md) over downgrading. The full rollback sequence is in
docs/upgrade.md.

## Adding a migration

After changing a model in `src/einfachllm/db/models.py`, autogenerate against a
throwaway database:

```bash
rm -f /tmp/einfachllm_autogen.db
DATABASE_URL=sqlite+aiosqlite:////tmp/einfachllm_autogen.db \
  uv run alembic revision --autogenerate -m "describe the change"
```

**Review the generated file before committing.** Autogenerate misses things: a
column rename looks like a drop + add (which loses data), server-side defaults
on existing columns, and constraints Alembic cannot introspect. Adjust
`upgrade()` and `downgrade()` by hand where needed.

Then verify it applies cleanly and matches the models:

```bash
rm -f /tmp/einfachllm_verify.db
DATABASE_URL=sqlite+aiosqlite:////tmp/einfachllm_verify.db uv run alembic upgrade head
DATABASE_URL=sqlite+aiosqlite:////tmp/einfachllm_verify.db uv run alembic check
# "No new upgrade operations detected." means the migration matches the models.
```

Finally test the round trip — upgrade, downgrade, upgrade — so the
`downgrade()` you just wrote is not fiction.

Generated migrations are not hand-edited after review lands; write a new
revision instead.

## Bringing an existing dev database under Alembic

For a database created by `create_all` that you don't want to rebuild:

```bash
uv run alembic stamp head
```

This records the current revision without running any migration. Only correct
when the schema really is at head.
